SUGGESTED WALKTHROUGH FOR THE EXAMINER
--------------------------------------------------------------------------------

1. CLIENT VIEW - the problem the system solves
   Sign in as 0201000201 (Ama Serwaa).
   The susu card shows every day of the cycle as paid, missed or pending, using
   a symbol AND a colour so it reads in sunlight and for colour-blind users.
   Below it, every payment recorded against her, each naming the collector who
   recorded it and the time. This is the independent record a paper card cannot
   provide.
   Note the REVERSED / REVERSAL pair near the top: a correction, with the
   original still visible. Nothing is ever deleted.

2. COLLECTOR VIEW - daily collection
   Sign in as 0244000101 (Joseph Osei).
   The route sheet lists only his own clients. Tap "Collect" on any client to
   record a contribution; the running total updates without a page reload.
   Tap "Collect" again on the same client to see the duplicate refused (BR-R5),
   with the existing reference quoted back.
   Open any client, then "QR card", to see the printable card.

3. AUTHORISATION - the photographed-card threat
   While signed in as 0244000102 (Kwame Tetteh), open a client belonging to
   Joseph Osei:
     https://susubook-fdtbppd7sq-uc.a.run.app/c/<any of Osei's client refs>
   The request is refused with 403 "This client is not on your route", and the
   attempt is written to the audit log. Possession of a client's QR reference
   confers no capability.

4. SUPERVISOR VIEW - oversight
   Sign in as 0244000100 (Mariama Adjei).
   The variance screen compares what each collector recorded in the field
   against the cash they declared at the branch.
   "Payouts" lists matured cycles with the settlement computed; releasing one
   closes the cycle and opens the next automatically.
   "Reverse" corrects a contribution by linked reversal, never by deletion.

NOTES ON THE DEPLOYMENT
--------------------------------------------------------------------------------

FIRST REQUEST MAY TAKE A FEW SECONDS
  The service scales to zero when idle, so the first request after a quiet
  period waits for a container to start - measured at 3.3 seconds. Subsequent
  requests are around 0.6 seconds. This keeps the running cost at zero and is
  documented as a deliberate trade-off in Project_Documentation.pdf, section 13.

HOSTING
  Google Cloud Run (region us-central1), against PostgreSQL 16 on a Compute
  Engine VM inside the same VPC. The database has no public address and is
  reachable only from within the VPC.

LATENCY
  us-central1 is roughly 150-200 ms from Ghana. It was chosen for Compute Engine
  free-tier eligibility rather than for proximity to the intended users, and
  measurement shows that latency dominating every request. This is recorded as a
  known limitation, not an oversight - see section 12.7 and section 17.5.

DATA
  All data is demonstration data created by the seed script. No real client
  information is stored.
